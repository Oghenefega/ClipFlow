### BLOCKER (5)

**Any error during startup leaves an invisible zombie process — no window, no error, and the app can never be relaunched**

- *Lane:* `crash-and-dataloss` · *effort:* trivial · *on the board:* unfiled
- *What happens:* The tester double-clicks Corva. The splash never appears. No error box, no message, nothing. A hidden Corva process is running in Task Manager holding the app's "only one copy at a time" lock, so every further double-click does absolutely nothing — silently. The only escape is knowing to open Task Manager and kill the orphan. For a beta tester this reads as "the app is dead and won't open," and there is nothing on screen to report. I reproduced this twice end-to-end on the dev profile (corrupt database, and a zero-byte settings file): in both runs the process was still alive and window-less when I killed it after 25-35 seconds.
- *Evidence:* src/main/main.js:729 opens the whole startup sequence as `app.whenReady().then(async () => {` and src/main/main.js:932 closes it with a bare `});` — there is NO `.catch()`. Inside it, two unguarded awaits run before any UI exists: main.js:745 `store = await createStore({ name: "clipflow-settings", defaults: STORE_DEFAULTS });` and main.js:762 `await database.init();`. The window is only created 158 lines later at main.js:920 `createWindow();`. Verified Electron 40.9.1 treats unhandled rejections as warn-only (test harness: process stayed alive after an unhandled rejection), so the throw does not kill the process — it just abandons the bootstrap. The zombie keeps the lock taken at main.js:42-44 `if (!app.requestSingleInstanceLock()) { app.exit(0); }`, and the recovery path is dead because main.js:618-619 reads `app.on("second-instance", () => { if (!mainWindow || mainWindow.isDestroyed()) return;` — mainWindow is null, so relaunches no-op. Observed run 1: `Error: database disk image is malformed at Object.init (src/main/database.js:267:6) at async src/main/main.js:762:3` then EXIT=124 (timeout kill, never self-exited). Observed run 2: `SyntaxError: Unexpected end of JSON input ... at createStore (src/main/store-factory.js:21:10) at async src/main/main.js:745:11`, EXIT=124.
- *Fix:* Wrap the whenReady body in try/catch (or append `.catch()` at main.js:932). On failure call `dialog.showErrorBox()` naming the offending file and its path, then `app.quit()` so the lock is released and the next launch is not swallowed. Independently, pass `clearInvalidConfig: true` in src/main/store-factory.js:20 so a corrupt electron-store file self-heals to defaults instead of throwing (conf 15 defaults it to false — see node_modules/conf/dist/source/index.js:555, and the throw at :240). For the DB, catch the malformed-image error in database.js init(), rename the bad file to .corrupt-<timestamp>, and start a fresh one rather than propagating.

**The whole SQLite database is rewritten non-atomically on every save — one interrupted write bricks the app (this is the likeliest trigger of the boot brick)**

- *Lane:* `crash-and-dataloss` · *effort:* small · *on the board:* unfiled
- *What happens:* Corva keeps its database entirely in memory and dumps the complete file to disk after every change — every rename, every clip approve/reject, every label. The prod database is 460 KB today and grows. Each dump is a single overwrite in place with no temp file: if the machine loses power, Windows force-reboots for an update, or the app is killed mid-dump, the file is left half-written. SQLite then reports "database disk image is malformed" on next launch, which triggers the silent no-window brick above. What the tester loses: their entire renamed-recording library, rename history, custom labels, and all the approve/reject feedback that trains detection. There is no backup written and no recovery path.
- *Evidence:* src/main/database.js:313-318 — `function save() { if (!db) return; const data = db.export(); const buffer = Buffer.from(data); fs.writeFileSync(DB_PATH, buffer); }`. That is a bare in-place overwrite, no temp-file-plus-rename. There are 28 call sites of `database.save()` across src/main (main.js, feedback.js, naming-presets.js, title-caption-log.js, reconcile.js, ai-pipeline.js, file-migration.js), including one on shutdown at src/main/main.js:937 `database.close();` (inside `window-all-closed`), which is exactly when the OS is most likely to terminate the process. Confirmed the corruption is fatal on read: `new SQL.Database(zeroedBuffer)` throws `file is not a database`, and my zero-tail repro against the real dev DB produced `database disk image is malformed` at database.js:267. Contrast with electron-store, which already writes safely via the `atomically` package (node_modules/conf/dist/source/index.js:10) — the DB is the one store that does not.
- *Fix:* In database.js save(), write to `DB_PATH + ".tmp"`, fsync, then `fs.renameSync` over DB_PATH — rename is atomic on NTFS. Keep one rolling `.bak` (copy the previous good file before the rename) so even a torn rename has a fallback. Optionally coalesce the 28 call sites behind a short debounce to cut write volume, since each one rewrites all 460 KB.

**Editor preview is dead on .mkv recordings — the watcher accepts them, Chromium cannot play them, and nothing reports the failure**

- *Lane:* `cross-machine` · *effort:* small · *on the board:* unfiled
- *What happens:* A tester who records in MKV (OBS's long-standing recommended format, and still what most "best OBS settings" guides specify) gets their files detected, renamed, and fully processed — transcription, detection, subtitles all work, because that side is FFmpeg. Then they open the editor and see a black rectangle. No error, no message. The scrubber never moves, the duration reads 0, subtitles cannot be timed by eye, and the Auto-Reframe calibration step (the only way to turn a 16:9 recording into a vertical clip) is impossible because it needs a drawn video frame to place the crop boxes on. The clip can still be rendered blind, but the tester has no way to know what they are shipping.
- *Evidence:* src/main/main.js:987 — `const RAW_RECORDING_PATTERN = /^\d{4}-\d{2}-\d{2}[ _]\d{2}-\d{2}-\d{2}(-vertical)?\.(mp4|mkv)$/i;` (mkv is explicitly admitted at the front door). src/renderer/editor/components/PreviewPanelNew.js:1043-1048 — `const src = project?.sourceFile || clip?.filePath; ... return \`file://${src.replace(/\\/g, "/")}${cacheBuster}\`;` and :1083 `vid.src = videoSrc;` — the raw source recording is handed straight to a Chromium `<video>`. Chromium's media stack has no Matroska demuxer for H.264/AAC content. src/renderer/editor/components/PreviewPanelNew.js:2028-2050 — both `<video>` elements carry onTimeUpdate/onLoadedMetadata/onEnded/onPlay/onPause and NO `onError`, so the load failure is swallowed entirely.
- *Fix:* Two parts. (1) Immediate, cheap: add `onError` to both `<video>` elements in PreviewPanelNew.js and render an explicit banner naming the file and container ("Corva can't preview .mkv — remux to MP4"), so the failure is never silent. (2) Real fix, same shape as the fix #178 already proposes: probe the source at project-open with ffprobe (the probe call already exists for width/height) and, for a non-Chromium-playable container or codec, run a fast lossless remux `ffmpeg -i in.mkv -map 0 -c copy in.mp4` (video and audio untouched, seconds not minutes), repoint `project.sourceFile` at it, and preview that. Alternatively, gate at the watcher: drop `mkv` from RAW_RECORDING_PATTERN and tell testers to record MP4 — a one-line beta workaround, but it silently narrows the supported setup.

**Editor autosave reports success when the save actually failed, then marks the work clean — silent loss of everything the tester edited**

- *Lane:* `crash-and-dataloss` · *effort:* trivial · *on the board:* unfiled
- *What happens:* The editor autosaves about once a second while the tester works on subtitles, captions, cuts and sounds. If that save fails on disk — folder locked by antivirus or a cloud-sync client, disk full, project file gone — the main process reports the failure back as a normal reply rather than an error. The editor does not look at it. It clears the "unsaved changes" flag anyway and reports success. So the tester sees a clean, saved-looking editor, keeps working, closes the clip, and every edit since the last good save is gone. Nothing warns them, and because the dirty flag was cleared there is no prompt on exit either.
- *Evidence:* src/renderer/editor/stores/useEditorStore.js:1228 `const res = await window.clipflow.projectUpdateClip(project.id, clip.id, {...})` — the reply is captured but `res.error` is never tested. Line 1255 runs unconditionally: `set({ dirty: false, ...(changed ? { clip: next } : {}) });` followed by line 1256 `return true;`. The `catch` at line 1257-1259 (`console.error("Save failed:", e); return false;`) can never fire for a backend failure, because the handler resolves rather than throws: src/main/main.js:2429 ends `project:updateClip` with `} catch (err) { return { error: err.message }; }`, and src/main/projects.js:258-259 returns `{ error: "Clip not found" }` / `{ error: "Project not found" }` as ordinary values. The failing write itself is src/main/projects.js:154 `fs.writeFileSync(projectPath, JSON.stringify(project, null, 2), "utf-8");`. Autosave cadence is src/renderer/editor/stores/useEditorStore.js:28 `const AUTOSAVE_DEBOUNCE_MS = 800;`.
- *Fix:* At useEditorStore.js:1254, guard the state update: `if (!res || res.error) { console.error(...); return false; }` before `set({ dirty: false })`, leaving dirty true so the exit prompt still fires. Surface a visible "Couldn't save — check disk" toast in the editor chrome; a console-only failure is invisible to a tester. Closed issue #92 fixed the same false-success pattern for the AI Accept button — this is the autosave twin and was missed.

**Render always takes audio stream 0, ignoring the calibrated voice track — multi-track OBS users get clips with the wrong audio**

- *Lane:* `cross-machine` · *effort:* small · *on the board:* unfiled
- *What happens:* OBS Advanced output mode lets you record separate audio tracks, and a very common gaming layout is Track 1 = game, Track 2 = mic. Corva has a whole calibration wizard that asks the tester which track is their voice and uses that answer correctly for transcription, subtitles, waveforms, and detection signals. Guard with a probe: if the source has fewer than N+1 audio streams, fall back to stream 0 and log it, matching the `fallbackToFirst` behaviour ffmpeg.js:337 already implements for extraction. ### `HIGH` #158 — Segment-mode round trip (3w→1w→3w) merges segments across pauses and stretches timings

**Verdict:** STILL-LIVE (high confidence) · **fix effort:** medium

**What a tester hits.** A tester opens a clip, clicks the subtitle style dropdown from "3 Words" to "1 Word" to see what it looks like, then switches back to "3 Words". **Evidence.**

REPRODUCED empirically by running the real production code.
